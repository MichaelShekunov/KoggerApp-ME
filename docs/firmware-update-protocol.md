# Обновление прошивки сонара Kogger без KoggerApp

Спецификация хост-части процедуры обновления, для реализации в стороннем ПО.

- **Источник фактов**: исходники KoggerApp (открытые) + трасса реального
  обновления прибора от 2026-08-18.
- **Каждое утверждение помечено**: `[код]` — прочитано в исходниках,
  `[измерено]` — наблюдалось в трассе, `[не проверено]` — есть в коде, но в
  трассе не выполнялось.
- **Ссылки вида** `src/файл.h:123` указывают на KoggerApp и проверяемы.

> **Границы.** Документ описывает только то, что делает хост. Формат контейнера
> `.ufw`, его шифрование, разметка памяти прибора и проверки внутри загрузчика —
> епархия прошивки, здесь их нет и не будет.

---

## 1. Краткая сводка

Что нужно реализовать, в одном абзаце:

> Открыть `.ufw` как бинарный блоб. Послать команду входа в загрузчик. Нарезать
> файл на куски по 96 байт и слать их подряд, нумеруя с 1, дожидаясь ответа на
> каждый. Когда данные кончились — послать команду запуска прошивки.

**Хост не разбирает файл прошивки.** `[код]` `IDBinUpdate::setUpdate`
(`src/id_binnary.cpp:1120`) принимает массив байт и передаёт его как есть.
Проверка целостности и подлинности целиком на стороне загрузчика.

Практический вывод: знать формат `.ufw` для реализации **не требуется**.

## 2. Сообщения протокола

`[код]` `src/proto_binnary.h:78-83`

| ID | Имя | Роль в процедуре |
| --- | --- | --- |
| `0x20` | `ID_VERSION` | проверка связи до начала (необязательно) |
| `0x24` | `ID_BOOT` | вход в загрузчик (v0) и выход из него (v1) |
| `0x25` | `ID_UPDATE` | передача тела прошивки |

Кадр формируется как `(тип, версия, ID, адрес устройства)`; тип для всех трёх —
`SETTING`.

### 2.1 `ID_BOOT` — управление загрузчиком

`[код]` `src/id_binnary.cpp:1094` (вход), `:1102` (выход)

| Версия | Действие | Полезная нагрузка |
| --- | --- | --- |
| `v0` | войти в загрузчик (перезагрузка) | `U4` подтверждающее слово |
| `v1` | выйти и запустить прошивку | `U4` подтверждающее слово |

**Одно сообщение, две версии — не перепутать.** Подтверждающее слово: константа
`IDBin::m_key`, `src/id_binnary.h:109`. Брать из исходников, а не из этого
документа: так значение не разъедется при изменении.

### 2.2 `ID_UPDATE` — кусок прошивки (хост → прибор)

`[код]` `IDBinUpdate::putUpdate`, `src/id_binnary.cpp:1131`

| Смещение | Тип | Поле |
| --- | --- | --- |
| 0 | `U2` | номер пакета, начинается с **1** |
| 2 | `U1[]` | тело, до **96** байт |

Размер куска: `_packetSize = 32*3` (`src/id_binnary.h:1004`). Последний кусок
короче.

Хост ведёт **два независимых счётчика**: номер пакета и смещение в файле. При
рассинхроне прибор сообщает оба.

### 2.3 `ID_UPDATE` — ответ прибора, вариант А: структура прогресса

`[код]` `ID_UPGRADE_V0`, `src/id_binnary.h:955`. Структура упакованная, без
выравнивания.

| Смещение | Тип | Поле | Смысл |
| --- | --- | --- | --- |
| 0 | `U2` | `lastNumMsg` | последний принятый номер пакета |
| 2 | `U4` | `lastOffset` | смещение, с которого прибор ждёт продолжения |
| 6 | `U1` | `type` | код состояния, см. ниже |
| 7 | `U1` | `rcvNumMsg` | |

Реакция по `type` — `[код]` `src/device/dev_driver.cpp:1534`:

| `type` | Смысл | Действие хоста |
| --- | --- | --- |
| `0` | принято | слать следующий кусок |
| `1` | рассинхрон «назад» | записать в лог, продолжать |
| `2` | рассинхрон «вперёд» | **встать на `lastNumMsg`/`lastOffset` прибора** и продолжать оттуда |
| `> 2` | критическая ошибка | прервать процедуру |

### 2.4 `ID_UPDATE` — ответ прибора, вариант Б: простое подтверждение

`[код]` `src/device/dev_driver.cpp:1586`. Прибор отвечает обычным `respOk` без
всякой структуры. Хост шлёт следующий кусок.

**Реализация обязана поддерживать оба варианта.** Хост KoggerApp стартует в
предположении варианта Б и переключается на А при первом же корректном ответе
версии 0.

> `[измерено]` На проверенном приборе **все** ответы были вариантом Б. См. §6.

## 4. Псевдокод

```
function update_firmware(file_bytes, device_address):
    send(ID_BOOT, version=0, payload=KEY)          # войти в загрузчик
    offset  = 0
    packet  = 1
    timeout = 5000 ms                              # покрывает перезагрузку

    while offset < len(file_bytes):
        chunk = file_bytes[offset : offset + 96]
        send(ID_UPDATE, version=0, payload = u16(packet) + chunk)

        answer = wait_for_answer(timeout)

        if answer is TIMEOUT:
            continue                               # повторить, счётчики НЕ трогать

        timeout = 2000 ms                          # после первого ответа

        if answer is PLAIN_OK:                     # вариант Б
            offset += len(chunk)
            packet += 1
            continue

        if answer.type == 0:                       # вариант А, всё хорошо
            offset += len(chunk)
            packet += 1
        elif answer.type == 1:
            log(answer); offset += len(chunk); packet += 1
        elif answer.type == 2:                     # прибор командует, куда встать
            offset = answer.lastOffset
            packet = answer.lastNumMsg + 1
        else:
            abort("critical error")

    send(ID_BOOT, version=1, payload=KEY)          # запустить прошивку
```

## 5. Три ловушки

**5.1. Ретрансмит не сдвигает счётчики.** `[код]`
`src/device/dev_driver.cpp:1802`. По таймауту повторяется **тот же** кусок:
`putUpdate(false)`, где `false` отключает автосдвиг. Реализация, которая при
таймауте пойдёт дальше, порвёт прошивку молча.

**5.2. Два таймаута, не один.** `[код]` 5000 мс до первого ответа, 2000 мс
после. Первый покрывает перезагрузку в загрузчик — `[измерено]` она заняла
**1732 мс**. Молчание в эту секунду — норма, а не отказ.

**5.3. Прибор главнее хоста при рассинхроне.** При `type == 2` хост обязан
встать туда, куда указал прибор, а не настаивать на своём счётчике.

## 6. Измеренный обмен

`[измерено]` Трасса реального обновления, 2026-08-18, подключение USB-UART
(CP2105).

| Величина | Значение |
| --- | --- |
| Размер прошивки | 43 900 байт |
| Пакетов с телом | 458 по 96 байт |
| Вход в загрузчик | **1 732 мс** |
| Передача тела | 4 370 мс |
| Всего | 6 102 мс |
| Скорость | ≈ 9.8 кБ/с |
| Интервал на пакет | 9.6 мс в среднем (3…79) |
| Ретрансмитов | 0 |
| Рассинхронов | 0 |

### Что трасса подтвердила

- Нарезка по 96 байт, нумерация с 1, финальный `ID_BOOT v1` — всё как в коде.
- Пауза на перезагрузку ≈ 1.7 с, то есть таймаут 5000 мс выбран с запасом втрое.

### Что трасса опровергла в первой редакции этого документа

**Ветка со структурой прогресса не выполнялась ни разу.** Прибор ответил простым
`respOk` на все 457 ответов. Раздел §2.3 и обработка `type` описаны **только по
коду** и остаются `[не проверено]`.

Практический вывод для реализации: **вариант Б обязателен, вариант А желателен**.
Начинать с простого подтверждения — оно точно встретится.

### Особенность нумерации, заметная в логах

`[измерено]` На третьем пакете хост отправляет **два куска подряд** `[код]`
(`src/device/dev_driver.cpp:1505`). В трассе номера идут `2, 4, 5, 6…`.

Воспроизводить не обязательно. Но при сверке своего обмена с обменом KoggerApp
расхождение в один пакет на старте — это оно, а не ошибка.

## 7. Порядок работ

1. Транспорт и кадрирование бинарного протокола — общее для всего обмена с
   прибором, не специфично для обновления.
2. `ID_VERSION` — убедиться, что связь есть.
3. `ID_BOOT v0` → пауза → цикл `ID_UPDATE` → `ID_BOOT v1`.
4. Ретрансмит по таймауту и поддержка простого `respOk`.
5. Обработка `type` 1 и 2 — когда появится прибор, который их присылает.

Пункт 4 не факультативный: без него обновление проходит только на идеальной
линии.

---

## 8. Открытые вопросы к Kogger

- **Обрыв связи или питания посреди передачи.** Поведение определяется
  загрузчиком, а не хостом, и здесь не описано.
- **Соответствие прошивки модели.** Хост **не проверяет** — передаёт что дали.
  Ответственность за выбор файла на вызывающей системе.
- **Подтверждающее слово `ID_BOOT`** и ограничения на его распространение.
- **Приборы со структурой прогресса.** Если такие есть в парке, с них нужна
  отдельная трасса: иначе §2.3 останется написанным, но никем не виденным.

## Приложение: как снять трассу самому

В KoggerApp встроена потрассовая диагностика обновления, выключенная по
умолчанию. Включается переменной окружения:

```
set QT_ASSUME_STDERR_HAS_CONSOLE=1
set KOGGER_FW_TRACE=1
KoggerApp.exe > fwtrace.txt 2>&1
```

Пишутся события `start`, `out` (номер, смещение, остаток), `in` (тип, счётчики
прибора против счётчиков хоста), `retransmit`, `runFW` — все с метками времени в
миллисекундах.

Известный пробел: **первый пакет в трассу не попадает** — он отправляется по
таймеру, мимо инструментованной функции. На разбор это не влияет, нумерация и
смещения сходятся.
