# Обновление прошивки сонара без KoggerApp

Описание процедуры для стороннего ПО. Составлено по исходникам KoggerApp —
приложение открытое, и всё описанное здесь можно перепроверить в нём же —
и **сверено с реальным обновлением прибора**, см. «Измеренный обмен» в конце.

**Границы документа.** Здесь только хост-часть: что и в каком порядке шлёт
управляющая программа и как она трактует ответы. Внутреннее устройство прошивки
и загрузчика — формат контейнера `.ufw`, его шифрование, разметка памяти,
проверки на стороне устройства — сюда не входит и предметом этого описания не
является.

## Главное в одной строке

Хост **не разбирает файл прошивки**. Содержимое `.ufw` передаётся в устройство
как есть, байт в байт, нарезанное на пакеты. Вся проверка целостности и
подлинности — на стороне загрузчика.

Это ключевой факт для реализации: сторонней системе не нужно знать ничего о
формате `.ufw`. Нужно уметь открыть файл, разбить на куски и вести протокол.

## Участвующие сообщения

Протокол бинарный, кадр создаётся как `(тип, версия, ID, адрес устройства)`.

| ID | Имя | Назначение |
| --- | --- | --- |
| `0x20` | `ID_VERSION` | запрос версии и серийного номера |
| `0x24` | `ID_BOOT` | вход в загрузчик и выход из него |
| `0x25` | `ID_UPDATE` | передача тела прошивки |

Кадры `ID_BOOT` несут четырёхбайтовое подтверждающее слово (константа
`IDBin::m_key`, `src/id_binnary.h`). Устройство сверяет его и отклоняет кадр без
совпадения. Значение брать из исходников, а не переписывать отсюда — так оно не
разъедется при изменении.

## Последовательность

### 1. Вход в загрузчик

Отправить `ID_BOOT`, **версия 0**, с подтверждающим словом. Устройство
перезагружается в загрузчик.

### 2. Передача тела

Файл нарезается на куски по **96 байт** (`_packetSize = 32*3`); последний кусок
короче. Каждый кусок уходит кадром `ID_UPDATE`, версия 0, тип `SETTING`, с
полезной нагрузкой:

```
U2   номер пакета   (начинается с 1, инкремент на каждый кусок)
U1[] тело           (до 96 байт)
```

Смещение в файле хост ведёт сам. Номер пакета и смещение — два независимых
счётчика, и при рассинхроне устройство сообщает оба.

### 3. Ответ устройства и реакция на него

На принятый кусок устройство отвечает кадром `ID_UPDATE` версии 0 со структурой
(упакованной, без выравнивания):

```
U2  lastNumMsg    последний принятый номер пакета
U4  lastOffset    смещение, с которого устройство ждёт продолжения
U1  type          код состояния
U1  rcvNumMsg
```

Реакция по `type`:

| `type` | Смысл | Действие хоста |
| --- | --- | --- |
| `0` | приём в порядке | отправить следующий кусок |
| `1` | рассинхрон «назад» | запись в лог, передача продолжается |
| `2` | рассинхрон «вперёд» | **перепозиционироваться** на `lastNumMsg` / `lastOffset` устройства и продолжить оттуда |
| `> 2` | критическая ошибка | прервать процедуру |

Тип `2` — штатный механизм восстановления: устройство само указывает, откуда
продолжать, и хост обязан ему подчиниться, а не настаивать на своём счётчике.

### 4. Завершение

Когда непереданных данных не осталось, хост отправляет `ID_BOOT`, **версия 1** —
команду покинуть загрузчик и запустить прошивку. Процедура закончена.

Обратите внимание на разницу: `ID_BOOT` версии 0 — войти в загрузчик, версии 1 —
выйти и стартовать. Одно сообщение, разные версии.

## Два механизма, без которых обновление рвётся

### Режим простого подтверждения (legacy)

Часть устройств не отвечает структурой прогресса, а подтверждает приём обычным
`respOk`. Хост стартует в предположении, что имеет дело именно с таким
устройством, и переключается на разбор структуры прогресса при первом же
корректном ответе версии 0.

Практический вывод: сторонняя реализация должна принимать оба варианта ответа. В
режиме простого подтверждения восстановления по смещению нет — есть только
«принято, шлите дальше», и любая ошибка ведёт к обрыву.

### Сторож по таймауту

Если ответа нет дольше таймаута, хост **повторяет тот же кусок, не сдвигая
счётчики**. Это ретрансмит, а не продолжение.

Таймаут: **5000 мс** до первого структурного ответа и **2000 мс** после. Первый
больше, потому что покрывает перезагрузку устройства в загрузчик.

## Мелочь, которая удивит при сверке с логами

На третьем пакете хост отправляет **два куска подряд**, а не один. Так сделано в
KoggerApp. Воспроизводить это не обязательно, но знать стоит: расхождение в один
пакет на старте при сравнении своего обмена с обменом KoggerApp — это оно, а не
ошибка.

## Порядок реализации, если начинать с нуля

1. Транспорт и кадрирование бинарного протокола — общее для всего обмена с
   прибором, не специфично для обновления.
2. `ID_VERSION` — убедиться, что связь есть и устройство отвечает.
3. `ID_BOOT` v0 → пауза на перезагрузку → цикл `ID_UPDATE` → `ID_BOOT` v1.
4. Обработка `type` 1 и 2, ретрансмит по таймауту, поддержка простого `respOk`.

Пункт 4 не факультативный: без него обновление проходит только на идеальной
линии.

## Измеренный обмен

Не вывод из кода, а запись реального обновления: прошивка 43 900 байт,
подключение через USB-UART (CP2105).

| Величина | Значение |
| --- | --- |
| Размер прошивки | 43 900 байт |
| Размер пакета | 96 байт |
| Пакетов с телом | 458 |
| Пауза на вход в загрузчик | **1 732 мс** (от команды до первого ответа) |
| Передача тела | 4 370 мс |
| Всего | 6 102 мс |
| Скорость | ≈ 9.8 кБ/с |
| Интервал на пакет | в среднем 9.6 мс (от 3 до 79 мс) |
| Ретрансмитов по таймауту | 0 |
| Рассинхронов (`type` 1 или 2) | 0 |

Три вывода, важные для реализации.

**Прибор отвечал простым `respOk` на все 457 ответов.** Структуру прогресса
(`ID_UPGRADE_V0`) он не прислал ни разу — то есть работал целиком в режиме
простого подтверждения. Ветка с `type`, перепозиционированием и восстановлением
по смещению в этом прогоне **не выполнялась ни разу**. Она описана выше по коду и
остаётся непроверенной на практике; на приборах этого поколения её, по-видимому,
не будет вовсе.

**Двойная отправка на третьем пакете подтверждена.** В трассе номера идут
`2, 4, 5, 6…` — пакет 3 уходит внутри той же операции и отдельным событием не
виден. Это не ошибка нумерации, а та самая особенность.

**Пауза на перезагрузку — около 1.7 с.** Первый таймаут в 5000 мс существует
именно ради неё и выбран с большим запасом. Сторонняя реализация должна ждать
ответа, а не считать молчание ошибкой.

## Что стоит уточнить до внедрения

- **Питание и обрыв связи.** Поведение устройства при обрыве посреди передачи
  определяется загрузчиком, а не хостом, и здесь не описано.
- **Совместимость версий.** Соответствие файла прошивки конкретной модели и
  ревизии хост не проверяет — он передаёт то, что ему дали.
- **Подтверждающее слово** `ID_BOOT` и ограничения на его распространение.
- **Приборы со структурой прогресса.** На проверенном экземпляре её нет. Если в
  парке есть модели, которые её присылают, стоит снять с них такую же трассу —
  иначе ветка восстановления по смещению останется написанной, но никем не
  виденной.
