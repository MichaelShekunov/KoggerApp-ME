# Два сонара на одной линии: видимость и обновление прошивки

Состояние на 2026-10-01: сделано в ветке `myedition` (0b07b67a), стоит на ПК. Движок проверен на
имитации кольца и на двух настоящих платах. Владелец увидел в приложении оба сонара и обновил их
кнопкой UPGRADE ALL ON THIS LINE — см. раздел «Проверка».

## Что это

Два сонара Basic2D с прошивкой кольца (версии 1.12 и новее) делят одну линию хоста:

```
хост TX → RX платы 1, TX платы 1 → RX платы 2, TX платы 2 → хост RX
```

У каждой платы свой адрес шины — байт маршрута кадра KP1: первая плата 1, вторая 2. KoggerApp заводит
отдельный прибор на каждый маршрут (`DeviceManager::getDevice(uuid, link, route)`), поэтому в
приложении это два сонара на одной линии, каждый со своими настройками. Прошивка кольца сама
синхронизирует пинги и пересылает кадры первой платы через вторую. Хосту свои команды назад не
возвращает: иначе KoggerApp разобрал бы их как ответы прибора с адресом 0.

**Порядок важен:** плата с меньшим адресом должна стоять первой (её RX — на TX хоста). На нём
построено обновление. Если кольцо собрано наоборот, обновление отказывает до первого пакета, ничего не
записав (проверено на имитации, см. ниже).

## Обновление

Штатное обновление KoggerApp в кольце не работает, по трём причинам:

* загрузчик стартует на 115200, а соседняя плата пересылает только на скорости линии;
* перебор скоростей идёт, только пока с линии не приходит ни одного целого кадра, а вторая плата
  продолжает слать;
* загрузчик слушает и отвечает на маршруте 0, а приложение шлёт и ждёт ответа на адресе прибора.

Поэтому у сонара с адресом 1…15 (`DevDriver::isRingBoard()`) кнопка **UPGRADE** запускает
`RingUpgrade` (`src/device/ring_upgrade.*`) вместо штатной процедуры. Кнопка **UPGRADE ALL ON THIS
LINE** запускает его для всех сонаров линии, начиная с последнего. Последний пересылает ответы
загрузчика первого, поэтому к нужному моменту он уже работает на новой прошивке.

Процедура на проводе — штатная (`docs/firmware-update-protocol.md`): `ID_BOOT` v0 → пакеты `ID_UPDATE`
по 96 Б с номерами от 1 → `ID_BOOT` v1 → `ID_VERSION` v2. Кольцо добавляет:

* **Кадры для загрузчика — на маршрут 16.** Загрузчик их берёт, плата с адресом 1…15 только
  пересылает. Ответы загрузчика идут с маршрутом 0; вторая плата их пересылает.
* **Первый контакт на 115200, потом загрузчик переводится на скорость линии** (`ID_UART` v0).
  * Вторая (последняя) плата: первая на долю секунды тоже переходит на 115200, хост слышит загрузчик
    напрямую.
  * Первая плата: хост шлёт смену скорости вслепую на 115200, а ответ слушает на скорости линии —
    через вторую.
  * К соседней плате движок обращается не раньше 150 мс после `ID_BOOT`, когда цель уже точно в
    загрузчике. Иначе при кольце, собранном наоборот, команда «перейди на 115200» прошла бы мимо цели к
    чужой плате и оставила бы её на 115200.
* **Пинги на время обновления выключены на всех платах линии** — в загрузчик не должен попасть
  синхронизирующий Break — и потом восстановлены. Плата, вернувшаяся после заливки со своими
  сохранёнными настройками, снова глушится до конца прогона.
* **Скорость линии закреплена** (`Link::setRatePinned`): без перебора скоростей и без опроса «все
  приборы». После первого пакета загрузчик молчит ~1.2 с, и перебор сорвал бы заливку. Кадры с
  маршрутом 0 во время прогона идут только движку: это загрузчик, а не отдельный прибор.
* **Проверка версии.** Версию, которую плата должна сообщить после заливки, движок берёт из имени
  файла (`_v1.12_`). Нет её в имени — не проверяет.

Ни один пакет прошивки не уходит, пока загрузчик не ответил на скорости линии. Отказ до этого
безопасен: через ~3 с плата сама возвращается в старую прошивку. Настройки остальных плат
восстанавливаются, когда она уже вернулась, — пока цель в загрузчике, первая плата перегораживает
путь ко второй. Обрыв посреди передачи оставляет плату в загрузчике; её тогда прошивают отдельно,
одну на линии.

### Поведение загрузчика, на которое опирается движок

Измерено на платах Basic2D, только то, что видно с линии:

| что | измерено |
|---|---|
| скорость после перезагрузки | 115200, первый ответ через ~0.4 с |
| маршрут ответа | 0 |
| кадр на маршрут 1 / 16 | без ответа / ответ |
| `ID_UART` v0 → 921600 | принимает |
| `ID_VERSION` | только v0, без v2 — загрузчик узнаётся по тому, что не отвечает на `ID_CHART_SETUP` |
| без пакетов прошивки | через ~3 с плата снова в своей прошивке |
| первый пакет / остальные | ответ через ~1.2 с / через ~10 мс |

## Проверка

`tools/ringupdate_check` собирает `RingUpgrade` отдельно от приложения.

* **Без железа:** имитация кольца, побайтовая по времени. В ней две платы с правилами пересылки
  прошивки кольца, их загрузчики с перечисленным выше поведением и скорости UART: кадр понят, только
  если приёмник на скорости отправителя. 13 сценариев, 26 проверок:
  * обновление последней, первой и обеих — в обоих порядках;
  * одиночная плата с адресом;
  * цель не уходит в загрузчик;
  * загрузчик не принимает смену скорости — у последней и у первой;
  * загрузчик умирает посреди передачи;
  * пакет потерян и отправлен повторно;
  * кольцо собрано наоборот, с медленной перезагрузкой;
  * не та версия;
  * негодные планы.

  Контрольный опыт: при ожидании 30 мс вместо 150 сценарий «кольцо наоборот» падает — первая плата
  остаётся на 115200 без пингов.
* **На железе** (`--live COMx --file F.ufw`): тот же класс обновил обе платы настоящего кольца за
  10.5 с (~3 с передачи на плату). После этого проверка кольца на стороне прошивки проходит целиком.
* **В приложении:** `KOGGER_AUTOTEST=<порт>` открывает порт сам, а
  `KOGGER_AUTOUPGRADE=<файл.ufw>|<all|адрес>|<число плат>` запускает обновление тем же путём, что
  кнопка, как только на линии ответит столько плат кольца. Итог — строки `ring-upgrade:` в
  `kogger.log`.
* **Кнопкой, владелец** (2026-10-01 12:10, сборка 0b07b67a на ПК): в списке приборов два сонара,
  UPGRADE ALL ON THIS LINE обновил обе платы за 11 с — по 469 пакетов, версия 1.12, без повторов
  (`kogger.log`). Уведомление «successfully flashed» пришло одно — по сонару открытой страницы;
  итог по второму есть только в журнале. После этого проверка кольца на стороне прошивки проходит
  целиком.
* **Серийные номера:** до прошивки 1.13 все платы отдавали один и тот же SN, поэтому оба сонара были
  в приложении с одним номером, и метка уведомления (`fw-upgrade-<SN>`) у них совпадала. С 1.13 номер
  у каждой платы свой, его считает прошивка.

```
cmake -G Ninja -S tools/ringupdate_check -B build/ringupdate_check -DCMAKE_PREFIX_PATH=D:/Qt/6.8.3/llvm-mingw_64
cmake --build build/ringupdate_check
build/ringupdate_check/ringupdate_check.exe
build/ringupdate_check/ringupdate_check.exe --live COM13 --file <образ>_v1.12_<...>.ufw
```

## За логгером (RECORDER Mini)

Проверено запросами через бошку 2026-10-01. Вверх логгер кольцо пропускает: кадры сонаров приходят в
KP2 с адресом, равным собственному маршруту сонара, — в приложении два сонара [1] и [2]. Вниз маршрут
кадра для логгера — номер его порта, а в порт он отдаёт кадр широковещательным: кадр сонару [2] получают
обе платы, кадр сонару [1] уходит в порт 1.

Поэтому сонару кольца, которого приложение видит за логгером (его кадры приходят в KP2), с прошивкой
1.14+ (`DevDriver::isRingBehindRecorder()`) команды уходят завёрнутыми: `ID_NODE_CMD` 0x7E на маршрут 0,
полезная нагрузка `[адрес сонара][режим][ID][данные]` (`DevDriver::onIdFrameOut`). Прошивка кольца
исполняет такую команду только на названном сонаре. Ответ приходит обычным путём.

Обновлять такой сонар через логгер нельзя: загрузчику нужен 115200 на порту, скорость которого логгер
держит сам. Вместо кнопок обновления страница сонара говорит подключить кольцо к компьютеру напрямую. По
той же причине сонар за логгером не считается сонаром кольца для `RingUpgrade` (`isRingBoard()` —
только кадры KP1).

Через настоящий логгер проверено 2026-10-01 (кольцо на порту SONAR 2, запросы с бошки): широковещательный
кадр с незнакомым ему ID 0x7E логгер в порт сонара отдаёт. На завёрнутый запрос версии ответил только
адресат; завёрнутая настройка для сонара 2 поменялась только у него, у сонара 1 осталась прежней. Киоск
headunit 567d840f шлёт сонарам кольца свои запросы обёрткой, и каждый сонар отвечает за себя (журнал
киоска). Глазами в интерфейсе киоска владелец проверил это 2026-10-01: настройка одного сонара кольца не
меняет другой (запись сессии киоска). На порту SONAR 1 кольцо не пробовалось.

## Адрес шины из приложения (2026-10-02)

Владелец: в поездке адрес плате задавать в KoggerApp, без Python. До этого его задавал только скрипт прошивки
`tools/bench/chain_addr.py`, а строка «Bus address» на странице сонара адрес лишь показывала.

Теперь у сонара Basic2D с прошивкой кольца (1.12+), не за логгером (`DevDriver::isBusAddressSettable()`), на
странице есть блок **Bus address**: выбор 0 / 1 / 2 и кнопка «Set and save address N». Установку ведёт
`BusAddress` (`src/device/bus_address.*`) в той же последовательности, что `chain_addr.py`:

1. Широковещательный GET `ID_UART` v1: ответ должен быть ровно один, иначе отказ («more than one board on the
   line»). С двумя платами на линии адрес могли бы взять обе. Счёт начинается через 150 мс после нажатия:
   ответ на запрос, который приложение послало прибору перед этим, не должен сойти за вторую плату.
2. SET `ID_UART` v1 `[key][1][адрес]` на маршрут 0, затем GET на новый маршрут должен прочитать адрес.
3. `ID_FLASH` v0 на новый маршрут — запись настроек во флеш: адреса и с ним всех текущих настроек платы.
4. Доказательство: адрес в памяти уводится (на 0, а при установке 0 — на 15), `ID_FLASH` v1 восстанавливает
   настройки из флеша, и GET на новый маршрут должен снова прочитать адрес. Несохранённый адрес вернуться
   не может.

Пока идёт установка (около 2.5 с), все кадры этой линии получает только `BusAddress`: иначе каждый
промежуточный маршрут стал бы отдельным прибором. Собственные кадры приборов этой линии на это время
отбрасываются (`Link::setDevicesMuted`), скорость линии закреплена (`Link::setRatePinned`). Иначе ответы платы
на опрос, который ведёт само приложение, попадут в счёт. Так и вышло в первой проверке внутри приложения
(2026-10-02, f18a7077, установка сразу после подключения): «2 answers to one request (2, 2)» при одной плате. При успехе `DeviceManager::rekeyDevice` переводит тот же
прибор на новый маршрут — страница, настройки и графики остаются. Прибор, уже сидевший на этом маршруте
(например, пустой, которого открытие линии создаёт на 0), удаляется. Строку «Bus address» затем обновляет
ответ платы, а не отправленное значение. При неудаче прибор остаётся на старом маршруте; если плата
успела взять новый адрес без записи, она появится отдельным прибором и после выключения вернётся к старому.

Проверка без железа — `tools/busaddr_check`: тот же класс против имитации плат с правилами кадров прошивки
кольца (одна плата или две в кольце), 14 проверок. Установка 0→1, 2→1, 1→0 (увод на 15) и во время пингов;
ответ платы на чужой запрос, пришедший через 40 мс после нажатия, — не вторая плата.
Отказ для кольца 1+2, для кольца с уже пронумерованной первой платой (случай 2026-10-01) и для двух плат на 0.
Отказ для прошивки без адреса и для пустой линии. Сбой записи во флеш пойман, и тогда, когда восстановление
из флеша тоже не работает. Адрес 16 отвергается до отправки. Контрольный опыт на копии класса: без увода
адреса перед восстановлением, без отказа на два ответа и без паузы перед счётом — все три мутанта пойманы. `--live COMx --set N` — тот
же класс на настоящей плате.

```
cmake -G Ninja -S tools/busaddr_check -B build/busaddr_check -DCMAKE_PREFIX_PATH=D:/Qt/6.8.3/llvm-mingw_64
cmake --build build/busaddr_check
build/busaddr_check/busaddr_check.exe
build/busaddr_check/busaddr_check.exe --live COM13 --set 1
```

В приложении без кликов: `KOGGER_AUTOTEST=<порт>` и `KOGGER_AUTOADDRESS=<адрес>` — установка тем же путём,
что кнопка, у первого подходящего сонара линии; итог — строки `bus-address:` в `kogger.log`.

## Скорость линии кольца (2026-10-03)

Владелец: в кольце нужны провода разной длины, значит, нужна другая скорость UART. Скорость у кольца одна на всю
линию. RX и TX платы — один USART1 (площадки PA10/PA9) с одним регистром скорости. Каждая плата пересылает байты
соседа как есть, поэтому и три участка «хост → плата 1 → плата 2 → хост» работают на одной скорости. Разные
скорости на участках ничего бы и не дали: последний участок несёт данные обеих плат и всё равно ограничивает
кольцо. Скорость выбирают по самому длинному проводу.

У сонара кольца (`isRingBoard()`) на странице есть блок **Line speed**: 921600 / 460800 / 230400 / 115200 и кнопка
«Set N for the whole line and save». Поле Baud rate у сонара кольца скрыто (`DevDriver::baudrateHidden()`): сменённая
на одной плате скорость рвёт кольцо. Смену ведёт `RingRate` (`src/device/ring_rate.*`):

1. У каждой платы читается `ID_DATASET`, пинги выключаются: линия молчит, Break не идёт на чужой скорости.
   Сначала у последней платы: её ответы идут хосту напрямую, а замолчав, она успевает переслать ответ первой.
   Запрос повторяется до трёх раз.
2. `ID_UART` v0 — сначала последней плате: первая ещё пересылает ей команду на старой скорости. Последняя
   отвечает на старой и переключается. Потом первой: её ответ теряется, последняя уже слушает на новой. Затем
   переключается порт хоста.
3. Обе платы должны ответить на GET `ID_UART` v0 на новой скорости и назвать её.
4. По одной плате, сначала первая: её пинги возвращаются как были, `ID_FLASH` v0, затем доказательство.
   `ID_FLASH` v1 перечитывает настройки из флеша; прошивка берёт оттуда и скорость, но применяет её только при
   старте. GET `ID_UART` v0 должен назвать новую скорость, GET `ID_DATASET` — пинги как были. Если пинги не
   вернулись, установка повторяется один раз. Пока заканчивается первая плата, последняя ещё молчит и
   пересылает её ответы.

До шага 3 ничего не записывается. Если на новой скорости кто-то не ответил, порт хоста возвращается на старую
скорость, а приложение просит выключить и включить обе платы: во флеше осталась старая. Пока идёт смена, около
3 с, линия принадлежит `RingRate`, как и при установке адреса: кадры приборов отбрасываются, скорость закреплена.
Плата, вернувшаяся после обновления прошивки, стартует на сохранённой скорости. Поэтому обновление в кольце
(`RingUpgrade`, `lineRate` = скорость линии) идёт на ней же, если её принимает загрузчик.

Оценка длины провода — расчёт, не замер. На стороне передачи 220 Ом, витая пара с землёй около 100 пФ/м, фронт
должен быть короче четверти бита. Получается: 921600 — до ~5 м, 460800 — ~10 м, 230400 — ~20 м, 115200 — ~40 м.
Помехи от передатчика сонара в расчёт не входят. Для десятков метров нужен дифференциальный интерфейс (RS-422),
а не TTL. Точность синхронизации падает вместе со скоростью: неопределённость — до одного бита, 1,1 мкс на 921600
и 8,7 мкс на 115200, это миллиметры дальности. За логгером RECORDER Mini скорость задаёт его порт, кольцо там
остаётся на 921600.

Проверка:

* **Без железа** — `tools/ringupdate_check`, та же имитация кольца со скоростями проводов, 17 новых проверок
  (всего 43/43):
  * кольцо 921600 → 460800 и → 115200;
  * одиночная плата → 230400;
  * кольцо, собранное наоборот, и плата, не принявшая скорость: отказ, ничего не записано, хост на старой
    скорости;
  * потерянная запись во флеш поймана доказательством;
  * 500000 — нет в таблице прошивки — отвергается до отправки;
  * обновление на кольце, работающем на 460800;
  * последняя плата при пингах теряет то, что пересылает (так было на железе на 115200);
  * два потерянных ответа `ID_DATASET` — повтор помогает; три — отказ, ничего не изменено.

  Контрольный опыт на копии класса (`-DRINGRATE_SRC`) — пять мутантов пойманы:
  * скорость сначала первой плате;
  * нет доказательства;
  * пинги не возвращены;
  * пинги сначала у первой платы — воспроизводит отказ с железа;

## Ограничения

* Две платы на линии. Адреса 1…15: маршрут 16 занят кадрами для загрузчика.
* Только Basic2D с прошивкой кольца. На старой прошивке нет пересылки ответов загрузчика — её первый
  переход на прошивку кольца делается по одной плате.
* Через Wi-Fi-модуль лодки (HeadUnit) пока не работает: там скорость меняет порт модуля, а не порт ПК.
