# Два сонара на одной линии: видимость и обновление прошивки

Состояние на 2026-10-01: сделано в ветке `myedition` (0b07b67a), стоит на ПК. Движок проверен на
имитации кольца и на двух настоящих платах. Владелец увидел в приложении оба сонара и обновил их
кнопкой UPGRADE ALL ON THIS LINE — см. раздел «Проверка».

## Что это

Два сонара Basic2D с прошивкой кольца (версии 1.12 и новее) делят одну линию хоста:

```
хост TX → RX платы 1, TX платы 1 → RX платы 2, TX платы 2 → хост RX
```

У каждой платы свой адрес шины — байт маршрута кадра KP1: первая плата 1, вторая 2. KoggerApp заводит
отдельный прибор на каждый маршрут (`DeviceManager::getDevice(uuid, link, route)`), поэтому в
приложении это два сонара на одной линии, каждый со своими настройками. Прошивка кольца сама
синхронизирует пинги и пересылает кадры первой платы через вторую. Хосту свои команды назад не
возвращает: иначе KoggerApp разобрал бы их как ответы прибора с адресом 0.

**Порядок важен:** плата с меньшим адресом должна стоять первой (её RX — на TX хоста). На нём
построено обновление. Если кольцо собрано наоборот, обновление отказывает до первого пакета, ничего не
записав (проверено на имитации, см. ниже).

## Обновление

Штатное обновление KoggerApp в кольце не работает, по трём причинам:

* загрузчик стартует на 115200, а соседняя плата пересылает только на скорости линии;
* перебор скоростей идёт, только пока с линии не приходит ни одного целого кадра, а вторая плата
  продолжает слать;
* загрузчик слушает и отвечает на маршруте 0, а приложение шлёт и ждёт ответа на адресе прибора.

Поэтому у сонара с адресом 1…15 (`DevDriver::isRingBoard()`) кнопка **UPGRADE** запускает
`RingUpgrade` (`src/device/ring_upgrade.*`) вместо штатной процедуры. Кнопка **UPGRADE ALL ON THIS
LINE** запускает его для всех сонаров линии, начиная с последнего. Последний пересылает ответы
загрузчика первого, поэтому к нужному моменту он уже работает на новой прошивке.

Процедура на проводе — штатная (`docs/firmware-update-protocol.md`): `ID_BOOT` v0 → пакеты `ID_UPDATE`
по 96 Б с номерами от 1 → `ID_BOOT` v1 → `ID_VERSION` v2. Кольцо добавляет:

* **Кадры для загрузчика — на маршрут 16.** Загрузчик их берёт, плата с адресом 1…15 только
  пересылает. Ответы загрузчика идут с маршрутом 0; вторая плата их пересылает.
* **Первый контакт на 115200, потом загрузчик переводится на скорость линии** (`ID_UART` v0).
  * Вторая (последняя) плата: первая на долю секунды тоже переходит на 115200, хост слышит загрузчик
    напрямую.
  * Первая плата: хост шлёт смену скорости вслепую на 115200, а ответ слушает на скорости линии —
    через вторую.
  * К соседней плате движок обращается не раньше 150 мс после `ID_BOOT`, когда цель уже точно в
    загрузчике. Иначе при кольце, собранном наоборот, команда «перейди на 115200» прошла бы мимо цели к
    чужой плате и оставила бы её на 115200.
* **Пинги на время обновления выключены на всех платах линии** — в загрузчик не должен попасть
  синхронизирующий Break — и потом восстановлены. Плата, вернувшаяся после заливки со своими
  сохранёнными настройками, снова глушится до конца прогона.
* **Скорость линии закреплена** (`Link::setRatePinned`): без перебора скоростей и без опроса «все
  приборы». После первого пакета загрузчик молчит ~1.2 с, и перебор сорвал бы заливку. Кадры с
  маршрутом 0 во время прогона идут только движку: это загрузчик, а не отдельный прибор.
* **Проверка версии.** Версию, которую плата должна сообщить после заливки, движок берёт из имени
  файла (`_v1.12_`). Нет её в имени — не проверяет.

Ни один пакет прошивки не уходит, пока загрузчик не ответил на скорости линии. Отказ до этого
безопасен: через ~3 с плата сама возвращается в старую прошивку. Настройки остальных плат
восстанавливаются, когда она уже вернулась, — пока цель в загрузчике, первая плата перегораживает
путь ко второй. Обрыв посреди передачи оставляет плату в загрузчике; её тогда прошивают отдельно,
одну на линии.

### Поведение загрузчика, на которое опирается движок

Измерено на платах Basic2D, только то, что видно с линии:

| что | измерено |
|---|---|
| скорость после перезагрузки | 115200, первый ответ через ~0.4 с |
| маршрут ответа | 0 |
| кадр на маршрут 1 / 16 | без ответа / ответ |
| `ID_UART` v0 → 921600 | принимает |
| `ID_VERSION` | только v0, без v2 — загрузчик узнаётся по тому, что не отвечает на `ID_CHART_SETUP` |
| без пакетов прошивки | через ~3 с плата снова в своей прошивке |
| первый пакет / остальные | ответ через ~1.2 с / через ~10 мс |

## Проверка

`tools/ringupdate_check` собирает `RingUpgrade` отдельно от приложения.

* **Без железа:** имитация кольца, побайтовая по времени. В ней две платы с правилами пересылки
  прошивки кольца, их загрузчики с перечисленным выше поведением и скорости UART: кадр понят, только
  если приёмник на скорости отправителя. 13 сценариев, 26 проверок:
  * обновление последней, первой и обеих — в обоих порядках;
  * одиночная плата с адресом;
  * цель не уходит в загрузчик;
  * загрузчик не принимает смену скорости — у последней и у первой;
  * загрузчик умирает посреди передачи;
  * пакет потерян и отправлен повторно;
  * кольцо собрано наоборот, с медленной перезагрузкой;
  * не та версия;
  * негодные планы.

  Контрольный опыт: при ожидании 30 мс вместо 150 сценарий «кольцо наоборот» падает — первая плата
  остаётся на 115200 без пингов.
* **На железе** (`--live COMx --file F.ufw`): тот же класс обновил обе платы настоящего кольца за
  10.5 с (~3 с передачи на плату). После этого проверка кольца на стороне прошивки проходит целиком.
* **В приложении:** `KOGGER_AUTOTEST=<порт>` открывает порт сам, а
  `KOGGER_AUTOUPGRADE=<файл.ufw>|<all|адрес>|<число плат>` запускает обновление тем же путём, что
  кнопка, как только на линии ответит столько плат кольца. Итог — строки `ring-upgrade:` в
  `kogger.log`.
* **Кнопкой, владелец** (2026-10-01 12:10, сборка 0b07b67a на ПК): в списке приборов два сонара,
  UPGRADE ALL ON THIS LINE обновил обе платы за 11 с — по 469 пакетов, версия 1.12, без повторов
  (`kogger.log`). Уведомление «successfully flashed» пришло одно — по сонару открытой страницы;
  итог по второму есть только в журнале. После этого проверка кольца на стороне прошивки проходит
  целиком.
* **Замечено:** прошивка сонара отдаёт одинаковый серийный номер на всех платах, поэтому оба сонара
  в приложении с одним SN, и метка уведомления (`fw-upgrade-<SN>`) у них общая.

```
cmake -G Ninja -S tools/ringupdate_check -B build/ringupdate_check -DCMAKE_PREFIX_PATH=D:/Qt/6.8.3/llvm-mingw_64
cmake --build build/ringupdate_check
build/ringupdate_check/ringupdate_check.exe
build/ringupdate_check/ringupdate_check.exe --live COM13 --file <образ>_v1.12_<...>.ufw
```

## Ограничения

* Две платы на линии. Адреса 1…15: маршрут 16 занят кадрами для загрузчика.
* Только Basic2D с прошивкой кольца. На старой прошивке нет пересылки ответов загрузчика — её первый
  переход на прошивку кольца делается по одной плате.
* Через Wi-Fi-модуль лодки (HeadUnit) пока не работает: там скорость меняет порт модуля, а не порт ПК.
